# Device notifications

Tracking: [delivery #74](https://github.com/mcclowes/machination/issues/74) and [incoming attacks #80](https://github.com/mcclowes/machination/issues/80), under [fidelity #18](https://github.com/mcclowes/machination/issues/18). This is the implementation contract; provider and device acceptance remain open.

## Reference and scope

Ron Carmel's [October 15, 2015 interview](https://www.gamedeveloper.com/design/-a-brawl-and-a-race-designing-for-the-long-game-in-i-subterfuge-i-) describes automatic push notifications for information players could not have predicted. This establishes a historical design principle, not the current client's complete trigger list. Incoming messages are the first rebuild interpretation of that principle. Exact current-original message preferences remain unobserved.

Native notifications cover incoming bilateral, private-group, and public-channel messages, plus separately enabled incoming attacks. Existing audience authorization applies, and senders receive no notification for their own messages. The separate contextual Alerts sheet remains [#75](https://github.com/mcclowes/machination/issues/75); no alarm options are inferred from its icon.

The publisher-linked [launch trailer](https://www.youtube.com/watch?v=WECvxdJv3kk&t=32s) shows an incoming-attack push with attacker, drillers, and ETA; at 94 seconds it shows the same information over the chart. This is staged alpha-era footage, also reused by the 2014 trailer and Steam Crossplay. Exact firing time, defaults, rounding, and bell linkage remain unknown. The rebuild chooses first observed threat detection, explicit device consent defaulting off, and a native foreground banner. These are documented interpretations, not current-original-client acceptance.

The worker settles active configured rooms with incoming consent every 60 seconds, even with no connected client. It detects newly observable hostile haulers aimed at the seat's sites or haulers. Preparing launches, private future plans, active gifts, own fleets, nearby traffic, and finished or eliminated seats produce no alert. Redirects, target capture, and ownership changes can create new threats. Each claim rechecks current authorized observations and renders the current attacker, drone count, and ETA rounded up to a minute. Alerts expire by arrival; a threat that departs and arrives entirely while the server is down produces no late alert.

## Device preference API

Both endpoints use the existing seat credential contract: a legacy seat bearer, or the configured Clerk account bearer resolved to that room's seat. Device IDs and bodies never select a recipient faction. Preferences do not settle game time, renew inactivity, change order revisions, or enter command replay.

- `GET /v1/games/:id/notifications?deviceId=<64 lowercase hex characters>` returns `MessageNotificationSettings`.
- `POST /v1/games/:id/notifications` accepts `SetMessageNotifications` and returns the same view.
- Adding `version=2` to either endpoint negotiates an `incoming` boolean. Version-two POST requires it. Default responses retain the exact legacy field set; version-one enable and token rotation preserve existing attack consent, and disable clears it. New clients retry a read without the version only after the old server's specific query-validation refusal; other failures do not downgrade.

Types live in [notifications.ts](../src/contracts/notifications.ts). A device ID is generated once per installation and kept in native secure storage. Requests use the existing request-ID syntax. The revision belongs to the device preference, independently of game orders. Set requests reject stale revisions; identical retries retained in a record return the current preference without reapplying an old enable. Disabled records retain their revision while stored. Evicting a disabled record raises a persisted seat revision floor above that record's last revision; unknown devices then read that floor, and old requests fail as stale. Responses expose no push token or credential hash.

An enabled registration requires a valid Expo push token; a disabled request omits it. A version-two consent-only write may omit the token only for an already enabled, current binding. It retains that binding and token; otherwise it fails with `notification.conflict.unbound`. Consent cannot attach or enable a device. Reject unknown fields and malformed values. Registration is bound to the authenticated credential generation, so account linking or legacy recovery invalidates old bindings. Tokens belong to at most one current binding across rooms; registering this physical installation for another seat detaches the former binding without exposing it. Keep bounded device records and active-device limits, and report capacity errors explicitly.

`available` reports whether the operator enabled server delivery. It does not certify provider credentials or device delivery. Disabled servers reject enable requests while still permitting disable, status reads, and tokenless withdrawal of attack consent. Migration leaves existing rooms unsubscribed. The first consent silently seeds threats at the present instant without changing the stored game; it does not backfill existing attacks.

Each seat keeps at most four device records, replacing its oldest disabled or invalidated record when necessary. Four active devices cause an explicit `notification.capacity.devices` conflict. Each record keeps sixteen request receipts. The server limits stored bindings to 40,000 and queued/in-flight jobs to 5,000 overall, with separate eight-job caps for messages and incoming attacks per binding; excess jobs are skipped while chat remains accepted. Each send has at most eight attempts within 24 hours, including attempts lost to expired leases or shutdown. Receipts are checked after fifteen minutes and retained for at most 24 hours after ticket acceptance.

## Durable delivery

Enqueue notifications in the same atomic transaction as an accepted new message. Use the message's actual audience, exclude its sender, and enqueue only for current enabled bindings. No old-message backfill occurs when enabling. Request retries, failed writes, and restarts must not create duplicate logical jobs. Notification failures must not undo an accepted message.

Messages use title `Machination`, body `New transmission received.` No message body, sender, or group name enters the payload. Separately consented attack alerts name the observed attacker, drone count, and ETA in their visible body, which can appear on a lock screen and passes through Expo. Routing data contains only kind, version, game ID, binding ID, and notification ID; no fleet IDs, credentials, recovery data, or hidden plans. Binding IDs are server-generated opaque values; notification IDs are stable across retries and also identify provider collapse/replacement fields.

The background worker claims bounded batches with durable leases, sends outside database transactions, records Expo tickets, and checks receipts. It handles backoff, invalid tokens, malformed responses, expiry, restart, disable, and credential invalidation. Background settlement touches only eligible rooms, renews no player activity, and adds no replay commands or order revisions. With no eligible room it skips the settlement write. A failing room is restored while others can commit. The observation ledger is server-only, outside saved games and replay archives. Message coalescing never swallows attack jobs. Closing the host stops new claims and drains or releases its current work within the existing shutdown grace period.

Expo's [delivery documentation](https://docs.expo.dev/push-notifications/sending-notifications/) distinguishes tickets from receipts and describes best-effort delivery. Stable IDs and collapse/replacement reduce duplicate presentation; exactly-once device delivery is not promised. Provider acceptance does not prove that a person received a notification.

## Native client

An explicit Message notifications action requests OS permission and registers the current installation. Reading settings or opening the app never requests permission. Denial, unsupported builds, token failures, unavailable servers, and unsuccessful disabling retain an honest state and a retry path. Opt-in state is scoped to the server, authenticated seat, game, and installation. Session changes and stale async completions cannot enable the wrong seat.

Use Expo SDK 55's native notification adapter; web and offline entry remain independent of it. Message banners are suppressed in the foreground because in-app Signals cover them. Valid incoming alerts use the native foreground banner and list, with no second custom banner. Message taps open Signals; incoming taps return to the live chart and clear forecast and hauler inspection. Both require the game and binding to match the restored authenticated operation, and incoming taps also require fresh attack consent. Each tap reads the current preference. Transient restore or settings failures keep it pending with Retry and Dismiss actions; a rejected seat, revoked consent, or confirmed mismatch consumes it. Deduplicate responses and clear consumed native response state. Never issue a game command or replace an active solo, practice, or replay session because a payload names another operation. Normal foreground connection and presence behavior still applies when multiplayer opens.

Attack consent is a second explicit action after enabling device notifications. Android prepares `machination-alerts` before that consent write; channel failure leaves consent off with a retry. Flag-only writes request neither OS permission nor an Expo token, and withdrawing consent needs no channel setup. Signing out does not revoke a device binding: the consent screen tells shared-device users to turn alerts off before signing out. Already delivered or in-flight OS notifications cannot be recalled.

The app requires a configured EAS project ID and native push capabilities. The operator controls server delivery separately. No Expo project, signing credential, deployment, OS permission, or live push is created by writing this code.

## Operator setup

Set `EXPO_PUBLIC_EAS_PROJECT_ID` to the existing Expo project's UUID before building the native app. The notification plugin includes the Android `machination-messages` channel configuration and a white notification icon. Physical iOS and Android delivery also need the project's APNs or FCM credentials and platform signing configuration. Adding this dependency requires a fresh native build; replacing only JavaScript in a pre-notification binary is insufficient.

The server defaults to delivery off. Set `MACHINATION_PUSH_ENABLED=1` to start the Expo worker; `0` or unset keeps it off, and other values refuse startup. Set server-only `EXPO_ACCESS_TOKEN` if the Expo project requires enhanced push security. Never expose that token as an `EXPO_PUBLIC_` variable. Enabling the worker reports availability, not successful credential validation.

After connecting a seat, open Setup and choose Turn on device notifications, then optionally Turn on incoming attack alerts after reading the disclosure. Legacy servers show message-only controls. Permission denial sends no enable request. Registration is only shown as enabled after a successful server response; a lost response can be retried safely. Turning device notifications off cancels all pending work and clears attack consent. Turning attack alerts off leaves messages enabled. Preference errors preserve explicit server details; a stale revision reloads the current setting before another change.

If an accepted enable response is lost and the token then changes, Retry first reconciles with the server. An enabled binding gets the current token; a later server-side disable stays off. A failed account restore keeps the tap pending until an explicit retry. An expired account credential while linking does not invalidate the existing device seat; a rejected device-seat credential still clears access.

Expo SDK 55 persists its native-token auto-registration after an opt-in and refreshes that mapping when the SDK next loads. The app loads it at startup after a prior registration and does not request permission or acquire a new Expo token on every launch. After a successful registration in the mounted seat, repeated native events for the same Expo token do not rewrite the subscription.

A token event during a preference write is retained for that seat. Repeated events coalesce into the latest token. After the write succeeds, or an unresolved failure is retried, the queued event reads the server preference before registering. A completed disable stays off, a later consent withdrawal is preserved, and leaving the seat discards pending rotation. This behavior is verified through the hook boundary, not native OS token events.

## Acceptance

Exact source `883831d`, isolated from concurrent working-tree edits, passes 1,004 regular tests, TypeScript, and three production-server build/restart checks on Node 24.14.1. The tested server-to-app path materializes an incoming attack with no connected client, feeds its actual payload through cold-start handling, and verifies fresh consent, the live chart, forecast reset, and no game writes. Legacy-server message taps and disabling also pass. Web, iOS, and Android exports pass; the [native package](native-builds.md#incoming-attack-notification-package) is signed and installed, with runtime and provider delivery still unverified. Local logs are `/tmp/machination-incoming-exact-check.log` and `/tmp/machination-incoming-export.log`.

Exercise actual service and HTTP boundaries for audience privacy, authentication, registration, revision and retry behavior, failed-write rollback, recovery/link invalidation, restart, and unavailable delivery. Use a fake provider for deterministic ticket, receipt, backoff, expiry, and shutdown scenarios; record that it does not prove real device delivery.

Drive real client state through permission denial, opt-in/off, reload, token rotation, account changes, network failure, and notification taps. Export web and native bundles, compile the native capabilities, and verify background/closed-app receipt and safe tap navigation on configured target runtimes before closing #74. Foreground logs, host tests, and successful packaging are insufficient delivery evidence.
